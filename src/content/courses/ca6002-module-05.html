第五周：AI Usability、Trust、Control 与 Feedback

第五周把 Human-Centred AI 落到具体 UX 设计：怎样让 AI 易学、易用、可恢复，怎样通过适当解释、信任校准、用户控制和反馈机制，让用户既不过度依赖，也不过度排斥 AI。

必须掌握的术语

术语考试级理解
utility产品是否具备解决用户问题的功能，即“能不能完成正确的任务”。课程强调 utility 先于 usability：功能不解决问题，再易用也没有价值。
usability特定用户在特定情境中，能否直觉、有效、高效且满意地使用产品实现明确目标。它是 UX 的组成部分，不等同于完整 UX。
user experience (UX)用户对产品整体体验与感受，除 utility/usability 外还包括 desirability、信任、价值、情绪与情境适配。
mental model用户对“系统如何工作、输入如何影响输出、系统会做什么/不会做什么”的内部理解。解释和一致性设计的目标，是建立足够准确而非技术细节最多的 mental model。
AI awareness让用户清楚某项功能或输出由 AI 参与，例如 sparkles icon、AI badge、品牌标识或生成内容标签；目的是设定正确期待并区分人与机器输出。
informative system feedback用户操作后，系统及时说明请求已收到、正在处理、可能等待多久以及是否完成，维持可见的 system status 与信任。
error / failureError 通常是可容忍的不准确或不符合期望，如推荐不相关；failure 使核心目标无法可靠完成或造成严重后果，如自动驾驶不停车。设计应容错，但不能把安全关键 failure 当普通误差。
system error / user errorSystem error 来自模型、训练数据、bias、feature weighting 等限制；user error 来自错误、模糊或不完整的交互输入。好的 UX 既帮助恢复，也预防错误。
competenceAI 是否能完成用户真正需要的任务并创造可识别价值；功能丰富或视觉漂亮不能代替任务能力。
reliabilityAI 是否持续、正确、可预测地执行其功能；基础功能较少但稳定，可能比功能多却时常失败更值得信任。
benevolence用户相信系统会维护其利益与自主性，结果准确、公平、无不当偏见，且不是以暗黑模式操控用户。
trust calibration用户信任程度应与系统实际能力相匹配。目标不是“信任越高越好”，而是知道什么时候接受、核实、覆盖或拒绝 AI 输出。
overtrust / distrustOvertrust：信任超过能力，用户不加判断地依赖；distrust：信任低于能力，用户忽略有价值建议。两者都会损害 Human-AI performance。
automation bias人倾向优先接受自动系统建议，甚至在与其他证据冲突时也停止搜索或核实；可造成 commission error（跟随错误建议）和 omission error（系统未提示便漏掉问题）。
explainability让适当的 stakeholder 理解 AI 如何/为何产生结果、系统表现如何及其边界，从而形成 mental model 并校准信任；不是把所有技术细节展示给每个人。
performance humility真实、及时地说明系统在哪些数据/情境表现好、哪里有限制，避免绝对语言；既不过度承诺，也不过分自我否定而削弱合理信任。
confidence level模型对某结果的内部置信程度，通常 0–1；不等于真实正确概率，除非模型经过良好 calibration。呈现形式可为 categorical、numeric 或 N-best。
controllability用户能够了解、调整、覆盖、撤销或退出 AI 的数据使用和输出。所需控制强度取决于风险、用户能力和任务情境。
graceful handoverAI 无法处理请求时，平滑转由用户或人工专家接管，并清楚说明发生了什么、已经收集什么信息和下一步是什么。
explicit feedback用户有意提供的反馈，如 thumbs up/down、Not interested、报告、评分、文字说明；信息明确，但会打断流程。
implicit feedback从行为或产品日志推断的反馈，如点击、观看时长、停留、跳过、搜索、眼动；规模大且自然，但可能含糊并带来隐私问题。

核心知识

Chapter 5.1 · HCAI UX Design — Usability

课件主线：Why usability matters → 五项 usability design → intuitive AI interactions → error handling → system errors → user errors。

1. Usability 为什么重要，又不等于 UX

高 usability 意味着特定用户在特定情境下，能以直觉、有效、高效和满意的方式实现定义清楚的目标。AI 产品的 usability 会直接影响 adoption 和 stickiness：用户第一次能否理解、重复使用是否省力、出错后能否恢复，决定其是否持续返回。

课程中的优先顺序可以写成：

Utility（解决正确问题） → Usability（容易正确使用） → Desirability（愿意持续选择）

例如把 Copilot 融入用户熟悉的 Word workflow，提高了 contextual assistance 与操作连续性；但若生成结果无法解决写作任务，单纯“嵌入 Word”并不能弥补 utility 缺失。

2. 五项 usability 评价维度

维度要问的问题AI 例子
Effectiveness用户能否准确完成目标？语音助手是否执行了正确设备、正确动作，而不仅是“听到了声音”。
Efficiency是否以较少步骤、时间和认知负担完成？AI 草拟邮件后允许直接选、改、发送，而非跨多个页面复制。
Engagement过程是否舒适、适合行业和任务？医疗 AI 应冷静清楚，娱乐推荐可更轻松；相同语气不适合所有领域。
Error tolerance系统能否接受合理的输入变化，并在错误发生时给出可理解反馈和恢复路径？拼写错误时提供 N-best candidates，而非只显示 exception code。
Ease of learning新用户是否容易开始，并能随使用快速熟练？首次显示 contextual tooltip，熟练后允许 dismiss/disable。

3. Intuitive AI interaction 的四类设计

设计点原则失败方式
Consistency使用已有 mental model：熟悉 icon、手势、菜单位置；web/mobile 在颜色、顺序与内容结构上保持一致。同一个 thumbs-up 在不同页面含义不同；移动端把关键功能藏到完全不同位置。
New-user supportTooltip 要 contextual、relevant、可触发行动且 easy to dismiss；只在需要时出现。永久遮挡内容、每次都重复、只解释术语却不给下一步。
Awareness of AI用 sparkles、AI badge、品牌 icon、生成标签让用户知道 AI 在何处参与。伪装为人工输出；或过度装饰使用户误以为普通功能都是 AI。
Informative feedback立即确认操作、显示 processing/progress、合理 ETA、完成结果和下一步。点击后无反馈，用户重复提交；虚假进度条或不可靠 ETA 反而损害信任。

4. AI awareness 设计的细节

  • Symbol：sparkles 已成为常见 AI cue，但并非正式标准；品牌如 Gemini/Copilot 应在不同集成场景一致使用。
  • Text badge：“AI”“Generated”“Rewrite with AI”比只有抽象图标更明确。
  • Colour：紫色和绿色常见，但没有通用规范，不能只靠颜色表达 AI 或状态。
  • 文化与可访问性：符号、颜色在不同社会可能有不同含义，应跨 demographic 做 user study，并提供文字/无障碍标签。

5. Informative feedback：尤其注意 voice UI

反馈应让用户知道系统是否正在听、请求是否已收到、是否在处理、任务是否完成。Alexa 的灯环、Google Assistant 的动态点属于 listening/processing cue；“Dining lights turned off”属于 completion confirmation。若操作需要较长时间，应显示动画和可信的 progress/ETA，让用户不把等待误认为系统坏掉。

6. Error 与 failure 必须先区分

类型例子设计含义
可容忍 error流媒体推荐了不感兴趣的电影。允许 dismiss/feedback、说明推荐依据、调整偏好。
system failure自动驾驶没有在红灯停车。核心安全功能不可接受；需 fail-safe、handover、监控与责任机制，不能只弹一句“抱歉”。
模糊边界音乐 app 无响应可能被视为 failure；推荐错歌是 error。应按用户目标、严重度、可恢复性和后果判断，而不是按工程团队标签判断。

7. AI system error 的四种处理策略

  1. Effective communication：用用户语言说明发生什么、为什么及如何恢复。“请加入 3 首歌，我们才能生成 playlist”优于“No playlist”或“Error 414”。
  2. 把误差变成 feedback moment：在错误预测旁提供低成本、情境化的 thumbs up/down 或正确类别反馈。
  3. 处理 user-perceived contextual error：系统按内部数据算得“最优”仍可能违背用户意图。应解释依据，并让用户调节 feature weight 或给明确反馈。
  4. 保护信任：承认局限、给恢复路径，不掩盖错误；但避免技术堆栈和无行动价值的 exception code。

8. User error：不责怪、消歧义、预防

  • 不责怪：避免“illegal command”“your input is incorrect”；改为“暂时无法处理，请检查日期并重试”。
  • Ambiguous input：“Did you mean Staying Alive by the Bee Gees?”；提供 N-best alternatives 让人判断。
  • Constraints：日期选择器限制 return date 早于 departure date；格式提示在提交前出现。
  • Scope upfront：健康 chatbot 显示可选任务类别，而非“Ask me anything”造成能力错觉。
  • Good defaults：提供 tomorrow、next week、1 hour 等合理值，减少输入成本并教会用户允许范围。

Chapter 5.2 · HCAI UX Design — Trust

课件主线：Components of trust → calibration → explainability/control → stakeholder explanations → 六项 explanation guidelines → confidence → user control → explicit/implicit feedback。

1. Trust 是动态关系，不是一次性标签

AI 会随着环境数据与用户互动变化，用户经验与信任也会变化。Trust 来自反复使用中形成的正向证据，核心成分为：

成分判断标准不能混淆
Competence真正完成任务并创造用户能感知的价值。不等于功能多、界面漂亮。
Reliability持续、正确、可预测；同类输入有稳定行为。不等于偶尔一次很惊艳。
Benevolence公平、尊重自主、维护用户利益。不等于友好语气；背后数据/商业做法也必须一致。

2. Trust calibration：正确匹配才是目标

Distrust:   user trust < actual capability → 忽略有价值建议
Calibrated: user trust ≈ actual capability → 适时接受、核实或覆盖
Overtrust:  user trust > actual capability → 无条件服从、自动化偏误

高信任不是永远的好事。过度信任可能因一次严重失败迅速反转为不信任；不信任则让 AI 投资无法产生效益。系统应帮助用户判断何时信、信多少、何时使用自身判断。

3. 建立信任的两大杠杆

  • Explainability：让用户理解系统如何工作、表现多好、输入如何影响输出、边界在哪里。
  • Control：允许用户选择数据、调整偏好、查看/覆盖输出、退出自动化或转人工。

课程总结强调 explainability 与 controllability 共同提供时，体验改善具有叠加作用。只解释但不给行动能力，用户仍无助；只给大量控制却不解释其后果，用户也无法正确使用。

4. 不同 stakeholder 需要不同解释

Stakeholder解释目的适当深度
被 AI 决策影响的人判断是否公平、哪些因素影响结果、如何申诉或改变输入。个案原因、关键因素、反事实与行动路径；避免模型数学。
使用 AI 做决定的专业人员判断是否采纳并结合领域情境。证据、confidence、限制、相似案例、override 与 audit trail。
ML / data engineers诊断、改进和监测模型。特征、数据漂移、错误分布、metrics、内部行为与日志。
审计/监管机构检查公平、安全、合规与事故。数据来源、治理、版本、测试、风险控制、可追溯记录。

5. 六项 AI explanation design guidelines

指南必须说明什么反例
1. System capabilities功能范围、适用任务、输入要求以及 AI 如何使用数据。只能搜菜谱却显示“Ask me anything”。
2. Performance humility在哪类数据表现好/差；使用概率语言；动态性能变化要及时更新。“一定正确”；或过度说“我什么都不知道”。
3. Adaptive behaviour系统如何随个人行为、环境和时间改变；为何今天结果与昨天不同。推荐悄然变化，用户以为系统随机或不可靠。
4. Input/output transparency收集哪些数据、来源、范围、是否个性化/全局聚合；输出为何产生、是否赞助。突然暴露个人信息，或把广告伪装成“附近最佳”。
5. Understandable explanation针对目标用户，简洁、透明、可访问；只解释影响判断与信任的关键内容。把模型全部技术细节倒给普通用户。
6. Confidence level选合适形式并提供 threshold/基线/行动语境；先做 user testing。展示未校准的 99%，诱发 overtrust。

6. Performance humility 的平衡

应说明系统训练边界，并用 positive/negative examples 教用户怎样获得好结果。例如植物识别系统可说“在光线明亮、背景简单的室内植物图像上表现最好”。语言上用“We think”“likely”“may”表达概率性，但仍要给明确建议。谦逊太少导致过度期待，太多则使用户认为系统没有价值。

7. Adaptive behaviour 与 transparency

  • 推荐系统应说明它会随着 watch/listen/rating 行为学习，新用户阶段可能较不准确。
  • 当 ETA 因天气和交通变得更慢、更不确定，应同时说明原因和 confidence，而非只改变数字。
  • 解释 personal vs global data scope：“基于你的收听记录”与“基于所有用户趋势”含义不同。
  • Specific example-based explanation 可展示与当前输入最相似的训练/检索样例，帮助人发现表面相似但语义不同的误判。

8. 三类 confidence explanation

形式优势风险与适用
CategoricalHigh/Medium/Low 易理解，并可直接映射动作。threshold 必须合理；类别太少会掩盖差异。语音助手可在 high 直接执行、medium 反问确认、low 请求重说。
Numeric信息精细，专业用户可用于 threshold decision。普通用户不知道 82% 是否足够；同一数值在音乐推荐和医疗诊断的意义不同，需基线、标签和后果语境。
N-best展示最高排名的多个候选，把最终判断交给用户。选项太多增加认知负担；适合低 confidence、搜索、语音消歧和人类判断有优势的场景。

关键警告：model confidence 不天然等于预测真实正确率。若 confidence 未 calibration 或在 distribution shift 下失真，精确百分比反而制造虚假确定性。

9. User control 应随风险调整

高风险场景（手术、刑事司法、金融）需要更多过程可见性、数据/算法监督、人工核准、纠正与审计；低风险场景（音乐推荐、商品搜索）可提高自动化，因为错误后果较轻。但即使低风险，也应允许 dismiss、reset 和 privacy opt-out。

控制类型设计要求例子
Graceful handover说明 AI 无法处理、无缝转人工、传递必要上下文、告知用户谁在接管。银行 chatbot 把诈骗咨询转给客服，并让客服看到已有对话。
Input data controlview/access/edit/share/opt-out；权限粒度要细；允许删除、修改、重置。允许 location 但拒绝 contacts；删除 YouTube history 或重置推荐。
Output control选择 N-best、调整 matching weights、覆盖或轻松 dismiss 不相关结果。Relevance Tuner；hover 后一键移除 newsfeed 推荐。

10. Explicit 与 implicit feedback

方面ExplicitImplicit
来源评分、survey、comment、thumbs、Not interested、report。click、dwell/watch time、skip、scroll、search、product log、eye tracking。
优势意图相对明确，让用户感到能纠正系统。自然、规模大、不要求用户额外操作。
局限打断 workflow、回应率低、可能有选择偏差。信号含糊：长时间停留可能是喜欢，也可能是困惑；隐私风险高。
设计要求时机/情境恰当；选项互斥、可理解、actionable；支持 undo/edit；解释反馈收益。告知收集和用途、取得 permission、允许 selective opt-out；用“Because you watched…”解释反馈如何影响输出。

Mid-week 05 Tutorial｜Usability 答题框架

M6.1 · Designing AI Interactions

Q1 Awareness of AI：Gemini vs Copilot

不要只写“都有 logo”。逐一观察并比较：

  • Before：输入区是否有 AI 品牌、生成按钮、prompt guidance，用户是否知道即将调用生成式 AI。
  • During：是否使用品牌 animation、sparkles、文字“Generating”等明确标识 AI processing。
  • After：输出是否标注 AI-generated、是否有 provenance/watermark、免责声明或编辑历史。
  • 评价：哪种设计既明确又不干扰主任务？是否仅依赖颜色？跨文化和无障碍是否足够？

高分句式：“A stronger awareness design labels AI participation at the action, processing and output stages; branding alone identifies the provider but may not sufficiently communicate that this particular artefact was generated by AI.”

Q2 Informative system feedback

比较 immediate acknowledgement、持续 processing cue、进度是否真实、等待时间、cancel/retry、完成提示和失败恢复。较好的设计不是动画更炫，而是减少 uncertainty：用户知道请求已收到、仍在运行、何时完成以及失败后怎么办。

Q3 Google Maps tooltip

UI 元素合理 tooltip 行为设计理由
Zoom短标签、快速出现。通用且低风险，熟悉用户不需长解释。
Show your location说明定位动作/状态，必要时关联 permission。涉及隐私与设备权限，需更清楚的预期。
Search / Directions提示输入目的或快捷操作。功能复杂度较高，应降低新用户学习成本。
Amenities显示类别名称，hover/selection 后可给地点语境。图标可能跨文化不明确，文字帮助识别。

M6.2 · Designing Error Handling

Q1 Non-existent website：三种浏览器比较维度

每个浏览器按四列写：accuracy（DNS/connection 原因是否准确）、message（普通人能否理解）、visual/tone（是否冷静、不责怪）、recovery help（检查拼写、连接、DNS、reload、diagnose）。最后明确偏好，并说明偏好来自更好的恢复能力而不是个人审美。

Q2 Missing webpage / 404

设计维度高质量表现低质量表现
Informative message明确页面不存在/已移动，不把责任推给用户。空白页、技术 stack trace、只有“404”。
Error tracking提供 reference ID 或 report link，后台记录 broken URL。要求用户重复描述所有技术信息。
Recovery搜索、主页、热门内容、返回上一页、相关链接。死路，无下一步。
Personalisation/branding在不掩盖问题的前提下，用相关内容或品牌缓解挫败。创意过度，用户反而找不到错误含义与出口。

迁移到 AI：404 的原则也适用于模型错误：说清发生什么、保持合适语气、给可执行恢复路径、记录/征求反馈，同时利用错误时刻建立正确 mental model。

Saturday 05 Tutorial｜Trust 答题框架

S5.1 · Trust Calibration

Q1 Automation bias

定义：用户因为建议来自自动系统而给予不当优先权，减少独立搜索、核验和判断，即使人类拥有相反证据也接受 AI。

机制怎样导致偏误
Anchoring / first plausible answerAI 第一个答案成为认知锚，人停止寻找替代解释。
Cognitive offloading / effort reduction核验需要时间与精力，接受自动建议更省力。
Perceived objectivity把数据驱动误认为无偏、全面和准确。
Authority / sophistication effect流畅语言、精确数字和复杂界面制造专业可信感。
Diffusion of responsibility人认为“系统负责”，降低自己的 vigilance。
Confirmation bias当 AI 与已有观点一致时，人更少检查；相反证据被忽略。

两类表现：commission error 是执行 AI 的错误建议；omission error 是 AI 没提示问题，人也因此漏掉。Mitigation 应覆盖 system、workflow 与 people：

  • 显示 limitations、data provenance、calibrated confidence 与 alternative hypotheses。
  • 高风险结果要求 independent check、second reader、checklist 或强制 justification。
  • 让人先形成初步判断再看 AI，减少 anchoring。
  • 设计易用的 override/appeal，不以默认或时间压力暗示“接受”。
  • 训练用户识别 automation bias，并用真实错误案例保持适度警觉。
  • 持续监测 override rate、错误类型与 human-AI joint performance，而不是只看 model accuracy。

案例答题模板：领域与决策 → AI 给出什么 → 人为何过度依赖 → commission/omission → 具体损害 → 哪些控制本可打断链条。可用“律师提交 ChatGPT 生成的虚假判例”说明：流畅输出被误作可靠法律检索，缺少 primary-source verification 与 citation checking，导致错误进入法庭文件并损害专业信誉。

Q2 Resistance to AI

可能驱动 distrust 的 perception：AI 不透明且不可预测；不能理解独特个案；威胁工作、身份、专业自主和地位；训练数据带偏见；隐私/监控风险；组织只是用 AI 降本；机器不应做需要同理心/道德判断的任务；早期负面体验被泛化。

Manager intervention 示例：针对“AI 会取代我”，不要只做宣传。采用 co-design workshop 让员工选择优先自动化的重复任务；把成功指标设为质量、负担与 customer outcome，而不是裁员；明确 human decision rights、override 与 accountability；提供 reskilling 和新角色路径；小范围 pilot、公开错误/收益数据并根据反馈迭代。这样同时回应 autonomy、identity 与 competence concern。

S5.2 · Designing AI Explanation

比较两个 chatbot 对 dog/rabbit 模糊图像的回答时，使用同一评价表：

维度应观察什么
Understandable是否指出耳朵、脸部轮廓等可见证据；解释是否简短、对应当前图像，而非泛泛谈模型。
Performance humility是否用“appears/likely/ambiguous”等承认不确定，又没有含糊到拒绝判断。
Confidence formnumeric、categorical 还是 N-best；是否给语境，数字是否伪精确。
Sequential adaptation第二张图是否引用第一张、解释差异并合理降低 dog confidence。
New-chat consistency无前文时对第二张图的判断是否与 sequential 情境合理一致；差异是否可解释。

关键分析：Sequential query 包含对话上下文，模型可能进行比较式判断；new query 只处理单图，结果差异不一定证明系统“错”，但若系统不解释上下文影响，就会降低 reliability perception。好的回答要把 consistency、adaptation 与 transparency 联系起来。

S5.3 · Designing User Control：WhatsApp

控制用户价值伦理权衡
Last seen and online控制 presence visibility，减少跟踪和即时回复压力。通常存在 reciprocity：隐藏自己时也可能看不到他人，兼顾双方公平。
Read receipts个人聊天中可关闭蓝勾，保护注意力与社交边界。通信是 people-to-people：一方隐私会影响另一方的沟通确定性；group chat 为协调与共同可见性可能采用不同规则。
Disappearing messages限制长期留存，降低历史消息暴露。不能保证绝对消失，截图、转发、备份仍可能存在；设计必须避免虚假安全感。
Storage management查看大文件/聊天占用、选择删除媒体、控制自动下载。避免 app 不透明地耗尽有限设备资源。
Data usage按 Wi-Fi/mobile/roaming 控制 media auto-download、通话低数据模式。在便利、费用、质量和用户自主之间平衡。

S5.4 · Designing User Feedback：YouTube

Explicit feedback

  • Not interested：推荐卡片附近的 contextual action，输入成本低；完成后应出现 Undo，符合 Shneiderman “permit easy reversal of actions”。
  • Don’t recommend channel：系统应说明反馈会怎样改变未来推荐，让用户理解提供反馈的 benefit。
  • Report：通过原因分类和补充说明进行 community policing；平台仍须复核，不能把内容治理责任全部转嫁给用户。
  • 设计检查：选项 mutually exclusive、可理解、可执行；“Other”需要开放说明；高风险/沉浸时刻不要强行弹出 survey。

Implicit feedback

YouTube 可从 impression、click-through、watch time、completion、rewatch、skip、pause、seek、search、subscription、session sequence 等推断兴趣，用于 ranking、个性化、广告和产品优化。但这些信号并不等价：watch time 长可能是喜欢，也可能是视频自动播放或用户困惑。

不希望个性化的用户应能清除/暂停 watch history、管理 activity、使用隐私/无痕选项及调整广告个性化。HCAI 重点不是“平台有设置”就够了，而是设置是否可发现、粒度是否合理、默认是否公平、退出后功能损失是否透明。

高频混淆与失分点

错误说法为什么失分正确表述
“Usability 就是 UX”忽略 utility、desirability 与整体体验。Usability 是 UX 的关键组成，位于解决问题能力之后。
“让用户更信 AI 就是成功”忽略 overtrust。目标是 calibrated trust，与实际能力匹配。
“Accuracy 高所以 confidence 可靠”总体 accuracy 不证明单样本 confidence calibration。区分 performance metric、individual confidence 和 calibration。
“解释越详细越好”普通用户会被技术细节淹没。解释应因 stakeholder、风险和任务而调整，简洁且 actionable。
“Error 都是用户输入错”系统/数据/模型也会产生 error。先区分 system vs user error，再设计预防和恢复。
“有人工在环就安全”人可能 automation bias、疲劳或没有实质 override。检查人是否有时间、能力、信息和权力进行独立判断。
“Implicit feedback 更真实”行为信号可能多义且带偏。结合多信号、解释用途、取得许可并提供 opt-out。
案例只描述功能没有连接设计原则与影响。写 evidence → principle → user consequence → trade-off → improvement。

考试答题模板与考前速记

设计评价五步法

  1. Define：准确给出课程概念。
  2. Observe：指出界面/流程中的具体证据。
  3. Explain：说明它如何影响 mental model、usability、control 或 calibration。
  4. Trade-off：同时写收益、限制、风险和情境差异。
  5. Improve：给可执行设计修改与衡量方式。

常见比较题句式

“Design A provides stronger informative feedback because it immediately acknowledges the request, maintains visible processing status and gives a recovery path. Design B only shows a decorative animation, so the user cannot distinguish delay from failure. However, A should avoid an ETA unless it can estimate it reliably.”

考前一分钟清单

必须能默写：五项 usability（effectiveness、efficiency、engagement、error tolerance、ease of learning）；四类 intuitive interaction；error vs failure、system vs user error；trust 三成分；distrust/calibrated/overtrust；explainability + control；四类 stakeholder；六项 explanation guidelines；categorical/numeric/N-best confidence；graceful handover、input/output control；explicit vs implicit feedback；automation bias 的 commission/omission 与 mitigation；任何案例都用 evidence → principle → consequence → trade-off → improvement。
